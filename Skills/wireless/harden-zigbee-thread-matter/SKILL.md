# Zigbee, Thread, and Matter Mesh Key Management - Defensive Methodology

> **Tier 2 - methodology skill.** No bespoke UMBRASEC detection rule ships with this skill yet. It gives the defender's method, the log sources and signals, the hunt, and the key-management hardening, and it points to public rule and standards sources. Promotion to Tier 1 (a sourced, tuned UMBRASEC rule) is tracked in [COVERAGE.md](https://github.com/umbrasec-labs/umbra-blue/blob/main/COVERAGE.md). Do not treat the content below as citing a UMBRASEC rule; there is none for this threat yet.

## TL;DR

These three mesh stacks all ride IEEE 802.15.4 and all live or die by how their keys are provisioned and how joining is gated. An attacker on the channel cannot break AES-128-CCM, but can capture a Zigbee network key when it is transported under the well-known default Trust Center link key `ZigBeeAlliance09`, force a device into an insecure rejoin, abuse touchlink to reset or steal a device, guess a weak or default Matter setup passcode while a commissioning window sits open, or petition as a rogue commissioner on a Thread network with a leaked PSKc. You almost never see the radio. You see the coordinator, the border router, and the Matter controller recording a join, a permit-join window, a commissioner session, or a new fabric. Close permit-join except during maintenance, provision Zigbee devices with per-device install codes instead of the global key, disable touchlink where you do not need it, keep setup passcodes and PSKc secret and rotate them, and ship the hub and border-router event streams to your SIEM. No single signal is conclusive on a busy home or building network; layer them.

## What it looks like, defender view

The attack surface is the join and commissioning path, where keys are introduced or renegotiated, and that path is logged by the controller rather than the radio. In Zigbee, a device joining with the default global Trust Center link key rather than a unique install code means the network key is transported in a form a sniffer can decrypt, so the join event itself is the exposure; a burst of `device_leave` then `device_announce` from one IEEE address is the classic forced-insecure-rejoin tell. Touchlink abuse surfaces as an unexpected identify, scan, or factory-reset of a device that no administrator touched. In Thread, a commissioner petition or a joiner appearing in the joiner table when nobody is onboarding points to a rogue commissioner or a leaked PSKc. In Matter, repeated failed PASE attempts during an open commissioning window are consistent with setup-passcode guessing, and a fabric count that increments without an administrator adding one means an unexpected controller now owns the device. None of this requires broken crypto; it requires RF access and a permissive commissioning configuration.

## Log sources and signals

The telemetry is the hub, coordinator, border router, and Matter controller. Ship these to your SIEM.

- **Zigbee via Zigbee2MQTT.** The `zigbee2mqtt/bridge/event` topic emits `device_joined`, `device_interview`, `device_announce`, and `device_leave`; `zigbee2mqtt/bridge/info` carries the current `permit_join` state and its timeout; `zigbee2mqtt/bridge/logging` carries the daemon log. Key provisioning lives in `configuration.yaml` (`network_key`, `pan_id`, `ext_pan_id`, `transmit_power`). Fields to lean on: the device IEEE address, the short (network) address, and the timestamp.
- **Zigbee via Home Assistant ZHA or deCONZ.** ZHA raises `zha_event` and device join/leave events through Home Assistant's event bus and logbook; deCONZ exposes equivalent join and configuration state over its REST and WebSocket API. Same identifiers: IEEE address, NWK address.
- **Thread via the OpenThread Border Router.** The `otbr-agent` syslog and `ot-ctl` state hold what you need: commissioner state, the `joiner` table, the active dataset (network key, PSKc, PAN ID, channel), and the leader/network-data view. A commissioner petition or a populated joiner table outside an onboarding window is the signal.
- **Matter via the controller.** Home Assistant's `python-matter-server`, `chip-tool`, or an ecosystem controller logs commissioning and session events. Beyond the log, poll two clusters on each node: the Operational Credentials cluster `Fabrics` list and `CommissionedFabrics` count, and the Administrator Commissioning cluster `WindowStatus`. An increment in the fabric count or a `WindowStatus` that shows an open window you did not open is the alarm.
- **Passive radio monitoring (optional, defensive).** Wireshark decoding 802.15.4 with your own network key loaded gives ground truth on join traffic and key transport. It is a monitoring aid, not an alert source.

What normal looks like, so the anomaly is legible: permit-join is closed almost all the time and opens only during a brief, operator-initiated maintenance window; a healthy device joins once and then only sends data and the occasional benign rejoin after a power cycle; the Thread joiner table is empty except during onboarding; and the Matter fabric count changes only when an administrator deliberately commissions the device onto a new ecosystem.

## Detection approach

Alert on the join and key-management events, because that is where capture, replay, rogue joining, and impersonation become visible and where false positives are lowest.

1. **Join or permit-join outside a maintenance window.** A `device_joined` on Zigbee, a Thread joiner, or a Matter commissioning window opening when no change was scheduled is the highest-value signal. Gate it on your own change calendar so an operator-initiated onboarding is expected and anything else alerts.
2. **Insecure rejoin and rejoin storms.** Repeated `device_leave` followed by `device_announce` from one IEEE address, or a device re-announcing far more often than its peers, is consistent with forced rejoin to re-expose the network key. Baseline per-device rejoin rate and alert on deviation.
3. **Default-key joining.** A device admitted with the global Trust Center link key rather than a unique install code means its key transport was decryptable. Make that an inventory and alerting condition: any join that is not install-code-backed is an exception to review.
4. **Touchlink anomaly.** An unexplained identify, scan, or factory reset of a Zigbee light or device is the touchlink-abuse signal. Where touchlink is not needed, disable it so any touchlink activity is by definition suspicious.
5. **Matter passcode guessing and new fabrics.** Repeated failed PASE attempts during an open window suggest setup-passcode brute force; the Matter specification requires the device to exit commissioning mode after 20 failed PASE attempts, so alert on the pattern of failures and on any increment in `CommissionedFabrics`.
6. **Thread rogue commissioner.** A commissioner petition or active-dataset change on the border router that no administrator initiated points to a leaked PSKc.

There is no widely maintained public Sigma ruleset dedicated to Zigbee, Thread, or Matter controller events today, so this skill does not point you at one that does not exist. The practical path is to normalize the Zigbee2MQTT or ZHA event stream, the otbr-agent log, and the Matter controller log into your SIEM and author the correlations above against those fields. Use the public SigmaHQ repository ([github.com/SigmaHQ/sigma](https://github.com/SigmaHQ/sigma)) as the format and category reference, the Zigbee2MQTT documentation ([zigbee2mqtt.io](https://www.zigbee2mqtt.io/)) and OpenThread documentation ([openthread.io](https://openthread.io/)) for the exact event and state identifiers your deployment emits, the Matter specification and cluster definitions from the Connectivity Standards Alliance ([csa-iot.org](https://csa-iot.org/)) and Project CHIP ([github.com/project-chip/connectedhomeip](https://github.com/project-chip/connectedhomeip)), and MITRE D3FEND ([d3fend.mitre.org](https://d3fend.mitre.org/)) for the countermeasure framing. A tuned UMBRASEC rule for this threat is not yet shipped; see the Tier 2 banner above.

## Threat hunt

Hypothesis: an attacker with RF access is capturing keys, forcing rejoins, or standing up a rogue commissioner or fabric against one or more devices.

1. Pull every join and leave event for the hunt window and group by IEEE address (Zigbee) or by joiner (Thread). Flag any address with more than a handful of join or rejoin cycles, and any device admitted without an install code.
2. Correlate every join and every permit-join opening against your change and maintenance calendar. Any join or open window with no matching change record is a candidate for rogue commissioning.
3. On Thread, read the border-router state and look for commissioner petitions, a non-empty joiner table, or active-dataset changes outside an onboarding window.
4. On Matter, enumerate the `Fabrics` list and `CommissionedFabrics` count on each node and reconcile against the ecosystems you expect. An extra fabric is an unexpected administrator. Check `WindowStatus` for any node sitting with an open commissioning window.
5. Review touchlink-capable Zigbee devices for unexplained resets or identify events, and confirm whether touchlink is enabled where it is not needed.
6. Rank by blast radius: a lock, garage controller, alarm sensor, or any actuator outranks a benign light or temperature sensor, because a stolen key or a hijacked device there has physical-security consequences.

## Hardening

Shrink the key and commissioning attack surface. Mappings below use control codes grounded in the UMBRASEC [governance and maturity guide](https://umbrasec.dev/guide/governance-and-maturity.html) and [identity and access guide](https://umbrasec.dev/guide/identity-and-access.html); a cell is left blank where no single control maps cleanly. The ASD Essential Eight is Windows-estate oriented and maps poorly to 802.15.4 mesh gear, so most of its column is blank by design, which is honest rather than a gap.

| Control | What it does | Essential Eight | ISO 27001:2022 | NIST CSF 2.0 |
|---|---|---|---|---|
| Provision Zigbee devices with per-device install codes | Derives a unique link key per device so capturing one join never yields the global key or the fleet | - | A.5.17 Authentication information | PR.AA-01 |
| Keep permit-join closed except for a brief maintenance window | Removes the standing opportunity to join, capture key transport, or force rejoin | - | A.8.5 Secure authentication | PR.AA |
| Disable touchlink where it is not required | Closes the unauthenticated proximity commissioning path used to reset and steal devices | - | A.8.5 Secure authentication | PR.AA |
| Protect and rotate Matter setup passcodes and Thread PSKc | Prevents passcode guessing during an open window and limits the value of a leaked commissioning credential | - | A.5.17 Authentication information | PR.AA-01 |
| Rotate the Zigbee network key and avoid the default TCLK | Limits the lifetime of a captured key and removes the `ZigBeeAlliance09` decryption path | - | A.5.17 Authentication information | PR.AA-01 |
| Keep hub, border-router, and device firmware current | Ships the Zigbee 3.0, Thread 1.2+, and Matter fixes that close commissioning and touchlink flaws | Patch operating systems | A.8.8 Technical vulnerabilities | PR.PS |
| Isolate the coordinator and border-router host on its own segment | Limits lateral reach from a compromised hub and keeps IoT traffic off the user LAN | - | - | PR.DS |
| Join, fabric, and commissioner logging and monitoring | Turns the join and key-management events above into alerts rather than silent drops | - | A.8.15 Logging; A.8.16 Monitoring | DE.CM; DE.AE |
| Device, fabric, and key inventory | Knows every IEEE address, every Matter fabric, and which key set each device carries, so an unknown joiner or extra fabric is visible | - | A.5.9 Inventory of assets | ID.AM |

## Honest limitations

This method watches the controller, so it cannot see an attacker who only passively captures 802.15.4 traffic and never joins, replays, or commissions; passive capture leaves no controller-side trace, and the defense against it is unique keys and firmware that does not leak them, not detection. A device that legitimately power-cycles often will generate benign rejoins that resemble a forced-rejoin pattern, so baseline per-device behaviour before alerting. Touchlink and commissioning signals depend on the hub actually logging them; some commercial hubs expose little or nothing, which is itself a reason to prefer a platform that does. Matter fabric and window state must be polled, so a short-lived open window between polls can be missed; prefer event-driven controller logs where available. On a dense network, legitimate maintenance and vendor app activity add noise that you must reconcile against a change calendar. Treat every signal as evidence to weigh, baseline in report-only mode first, and leave the final call to the defender.
