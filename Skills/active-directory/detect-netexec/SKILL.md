# NetExec - Defensive Methodology

> **Tier 2 - methodology skill.** No bespoke UMBRASEC detection rule ships with this skill yet. It gives the defender's method, the log sources and signals, the match logic in prose, the hunt and the hardening, and points to public rule sources. Promotion to Tier 1 (a sourced, tuned UMBRASEC rule) is tracked in [COVERAGE.md](https://github.com/umbrasec-labs/umbra-blue/blob/main/COVERAGE.md). Do not treat the content below as citing a UMBRASEC rule; there is none for this threat yet.

NetExec (`nxc`) is the community-maintained successor of CrackMapExec. One operator, one host and one set of credentials can test a password against every machine in a subnet, run a command on each machine that accepts it, and pull local and domain credentials back. Intrusions use it for exactly that; in the Lynx ransomware case published by The DFIR Report, the actor downloaded NetExec on day six and swept SMB on a /24 with domain admin credentials (Seen in logs: [DFIR Report, 2025-12-17](https://thedfirreport.com/2025/12/17/cats-got-your-files-lynx-ransomware/)). This skill is defensive: it describes NetExec only as far as a defender needs to recognise it in logs, and ships no usage guidance.

Each claim below carries its basis: **Their code** (read in NetExec, CrackMapExec or Impacket source), **Vendor docs** (Microsoft or the NetExec project), **Seen in logs** (a published incident or capture), or **Guess** (inference, not verified).

## TL;DR for defenders

Turn on process creation with command lines, **Audit Other Object Access Events** (4698) and **Audit Detailed File Share** (5145), and collect the System log for **7045**. NetExec runs remote commands through four methods, and each leaves a template that differs from Impacket's, which is why older CrackMapExec and Impacket rules miss much of it: the three detections described below key on NetExec's own templates (match logic in prose; no UMBRASEC rule ships yet). Pair them with Defender for Identity's brute force, pass-the-hash and DCSync alerts (written for the techniques, not for NetExec; see the alert table below), and hunt for one source address fanning NTLM logons with an empty workstation name across many accounts or hosts.

## What it looks like, defender view

NetExec is a Python tool that usually runs from the attacker's own Linux machine, so on your estate you see only the network side: logons, named-pipe and share access, and whatever it starts on each target. When it is run on a compromised Windows host, that host also shows the binary itself.

## Detection approach

Three detections keyed to NetExec's own templates, highest precision first, described as match logic you can express in Sigma, KQL or your SIEM's language, then an NTLM fan-out hunt, and the public rules and vendor alerts to run beside them. The logic was checked as draft Sigma rules with `sigma check` and against synthetic events built from NetExec, CrackMapExec and Impacket source; none has been run against a real capture yet, and no UMBRASEC rule ships for it.

### 1. smbexec service installed (System 7045)

Matches a service whose ImagePath is NetExec's smbexec template: `%COMSPEC% /Q /c echo`, a redirect into `%TEMP%\<name>.bat`, and a final `%COMSPEC% /Q /c del %TEMP%\` to remove it. A second branch catches the no-output form, a bare `%COMSPEC% /Q /c` command, but only under a 10-letter, letters-only service name, which is what NetExec generates (Their code). The same template was used by CrackMapExec, so it covers both. Impacket's smbexec does not match, and the SigmaHQ rule `52a85084` (smbexec.py Service Installation) covers Impacket but not NetExec: it looks for the `BTOBTO` name, `.bat & del ` or `__output`, none of which NetExec writes (Their code: both rule and tool; confirmed by local evaluation on code-derived samples). That 7045 shows `%COMSPEC%` literally rather than expanded is supported by the comments in SigmaHQ rule `843544a7`, which match getsystem services on the literal `%COMSPEC%` (Their code); not checked on a NetExec capture. The match therefore uses only tokens that survive either rendering (` /Q /c echo `, ` 2^>^&1 > `, `.bat & `, ` /Q /c del `), and the no-output branch accepts `%COMSPEC% /Q /c ` at the start or `\cmd.exe /Q /c ` anywhere; both an expanded and a literal ImagePath matched in local evaluation.


### 2. Remote command output staged by a service host (process creation)

Matches `cmd.exe` started by `WmiPrvSE.exe`, `mmc.exe`, `svchost.exe` or `taskeng.exe` whose command line redirects to `\Windows\Temp\` plus 6 to 8 letters (with the optional `/` NetExec adds when it runs on Linux), the smbexec batch-file pattern under `services.exe`, and the wmi protocol's `certutil -encodehex` and `reg add HKLM\Software\Classes\` steps. The redirect regex covered all 56 atexec spellings in local evaluation, where the SigmaHQ CrackMapExec rule `058f4380` matched 8 of 56 and the Impacket lateral movement rule `10c14723` matched 28 of 56 (Their code plus local evaluation; synthetic, not logs). Neither of those SigmaHQ rules matched NetExec's default wmiexec line, because both expect a UNC output path. Two branches cover the wmi protocol's PowerShell variant (`-X`): a `C:\windows\temp\<GUID>.txt` redirect from any `WmiPrvSE.exe` child, and the `[Convert]::ToBase64String([IO.File]::ReadAllBytes('C:\windows\temp\` step. `taskeng.exe` is accepted as the atexec parent for Windows 7 and Server 2008 R2, where it starts task actions (Their code: SigmaHQ `10c14723` lists it with the comment "atexec on win7"). What this detection cannot see: with `--no-output`, wmiexec, mmcexec and atexec drop the redirect (Their code: `smb/wmiexec.py` L112-113, `smb/mmcexec.py` L194-195, `smb/atexec.py`), so a no-output wmiexec or mmcexec run leaves only a bare `cmd.exe /Q /c <command>` under `WmiPrvSE.exe` or `mmc.exe`, which only generic rules such as SigmaHQ `d21374ff` catch. For no-output runs, only detection 1 (smbexec's 10-letter service) and detection 3 (atexec's task) still key on NetExec templates.


In Defender for Endpoint the same logic runs over `DeviceProcessEvents` (`FileName`, `InitiatingProcessFileName`, `ProcessCommandLine`; Vendor docs: [DeviceProcessEvents](https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-deviceprocessevents-table)). A `\Windows\Temp\/` path says the operator ran NetExec from Linux or macOS.


### 3. atexec scheduled task registered (Security 4698)

Matches a 4698 for a root task with an 8-letter name, a `RegistrationTrigger` and one of NetExec's 8 cmd spellings as the action, or any task whose XML holds the `\Windows\Temp\/` path. Impacket and CrackMapExec register a `CalendarTrigger` and do not match (Their code). Expect a 4699 for the same `TaskName`, usually within seconds, because NetExec deletes the task once it has run (Their code: `hSchRpcDelete`, v1.5.1 atexec.py L212; `main` polls for up to 30 seconds, then deletes). The task shape predates the 2025 randomisation, so the first selection also covers NetExec v1.4.0, which registered `<Command>cmd.exe</Command>` under a `RegistrationTrigger` (Their code). Windows Server 2025 changes the picture: NetExec `main` notes that "Win2025+ (build 26100): RegistrationTrigger does not start the task over remote TSCH" and calls `SchRpcRun` there (Their code: `main` atexec.py L159-164). v1.5.1 has no such call, so against Server 2025 a v1.5.1 task may register (4698) and never start any process. What happens next depends on the server's reply to the run-status poll: if it answers success with a zero run time, as MS-TSCH specifies for a task that never started (Vendor docs: [SchRpcGetLastRunInfo](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-tsch/fe8aa42f-7e37-4c00-80af-7de32272cecd)), v1.5.1 polls with no timeout and the task stays registered, with no 4699, until the operator stops it; if it answers `SCHED_S_TASK_HAS_NOT_RUN`, which NetExec `main`'s comments suggest happens, v1.5.1 treats that as an error and deletes the task at once (Their code: v1.5.1 L198-212 and Impacket `rpcrt.py` raising on any non-zero status). Which one Windows does is a Guess; either way a lingering or run-less root 8-letter `RegistrationTrigger` task is itself suspicious. Whether Windows stores the `<Command>` element exactly as sent in `TaskContent` is a Guess; Microsoft's example shows the task XML as registered (Vendor docs).


### 4. NTLM fan-out with an empty workstation name (hunt)

Spraying and pass-the-hash look like ordinary type 3 NTLM logons, one at a time. What gives NetExec away is shape: one source address, many accounts or many hosts, in minutes, with no client name (Their code; rendering a Guess). This is a hunt, not an alert, because other Impacket tools, vulnerability scanners and some Linux and appliance clients also send no workstation name. Microsoft notes that "NTLM logons have no TCP/IP details" in some cases (Vendor docs: event 4624), so rows with an empty or `-` `IpAddress` cannot be grouped by source; count those separately per target `Computer` (Guess: how often this happens for NetExec was not measured). In Sentinel, group `SecurityEvent` rows for 4624 and 4625 with `LogonType` 3, `AuthenticationPackageName` NTLM and an empty or `-` `WorkstationName` by `IpAddress` in 10-minute bins, and look at distinct `TargetUserName` and distinct `Computer` (Vendor docs: [SecurityEvent](https://learn.microsoft.com/en-us/azure/azure-monitor/reference/tables/securityevent)). Start at 10 accounts or 5 hosts.

### Tuning and false positives

- **Run all three detections report-only for two weeks.** They key on tool templates, so the expected benign rate is low, but nobody has measured it on a real estate yet.
- **Detection 1.** The no-output branch is the looser one. If a deployment tool installs short-lived `%COMSPEC%` services under 10-letter names, allowlist it by `ServiceName` pattern or by the installing account from the matching 4697 or 4624.
- **Detection 2.** The redirect regex matches any 6 to 8 letter, extensionless file name directly under `\Windows\Temp`, so an inventory or management tool that runs `cmd.exe` over WMI or a task and writes, say, `> \Windows\Temp\sysinfo 2>&1` matches (a drive-less admin control did, in local evaluation); allowlist by account and source host, not by path. A drive-qualified path such as `C:\Windows\Temp\netinfo` does not match, nor do SCCM `CcmExec.exe` children (local evaluation, synthetic). `svchost.exe` as a parent is broad, so the regex carries the precision; do not loosen it.
- **Detection 3.** Needs 4698 auditing, which many estates leave off. Baseline root-level tasks with `RegistrationTrigger` before alerting.
- **Hunt 4.** Start at 10 accounts or 5 hosts per source per 10 minutes, then set the bar above your noisiest scanner. Exclude vulnerability scanners and NAS or appliance subnets by address, not by account.
- **Authorised testing.** Red teams and penetration testers use NetExec. Agree a source-address list and a window, and keep the alert firing; close it as a benign true positive rather than allowlisting the tool.

### Triage

When one of the detections fires:

1. **Find the source.** For detections 1 to 3 the target host is in the event; the source is the matching 4624 type 3 on that host just before it (same account, `IpAddress`). Note the authentication package: NTLM with an empty workstation name fits NetExec; Kerberos does not rule it out.
2. **Scope the sweep.** Search every host for the same source address and account in the hour around the hit: 4624/4625 type 3, 7045, 4698/4699, and detection 2 matches. NetExec is built to hit many hosts at once, so one host rarely means one victim.
3. **Read the command.** The command line or the service ImagePath holds the operator's command in clear text. Credential-access commands, `reg save`, `comsvcs`, `ntdsutil`, or a file dropped in `C:\Windows\Temp\` move the case to credential compromise.
4. **Check for credential theft.** On the targets: a 5145 `IPC$` `svcctl` then `winreg` from the source with RemoteRegistry starting and stopping around it (7036, and 7040 if it was disabled) (SAM/LSA, both modes), `C:\Windows\Temp\<8 letters>.tmp` files or 5145 `ADMIN$` reads of `Temp\<8 letters>.tmp` (old mode), LSASS access or dumps. On DCs: DCSync signals (4662 replication GUIDs, MDI 2006).
5. **Decide on the accounts.** Any account that authenticated successfully from the source is presumed compromised. If SAM, LSA or NTDS were read, so are the local administrator hashes, cached domain credentials, service account secrets, or, for NTDS, every domain hash including `krbtgt`.
6. **Contain.** Isolate the source host if it is yours, block it if it is not, reset or disable the affected accounts, and plan a `krbtgt` double reset if NTDS was read. Hand the call to the incident lead; nothing here should fire an automated response unattended.

## Threat hunt

Hypothesis: someone has run NetExec on the estate without tripping an alert, by using Kerberos, by running one command per host, or before these rules existed.

1. **Fan-out by source.** Over 30 days, count distinct target hosts per source address for successful type 3 logons by a single account. A workstation that logs on to 50 servers in five minutes is the pattern, whatever the protocol.
2. **Named-pipe sweep.** With 5145, list sources that opened `svcctl`, `atsvc` or `winreg` on `IPC$` on more than a handful of hosts in a day. Those pipes are protocol endpoints, not NetExec-specific: `\PIPE\svcctl` is the Service Control Manager's assigned pipe on every Windows host (Vendor docs: [MS-SCMR standards assignments](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-scmr/e7a38186-cde2-40ad-90c7-650822bd6333)), even though SigmaHQ's `fe3ac066` comments it as a CrackMapExec smbexec pipe. The signal is breadth, not the name. NetExec's admin check opens `svcctl` on every host where a sprayed or reused credential works, before any execution (Their code: `check_if_admin`), so join this to the fan-out in step 1 by source `IpAddress`: the same source with type 3 logons and `svcctl` opens on many hosts is an authentication sweep that found admin rights.
3. **Short-lived services and tasks.** Pair each 4698 with a 4699 for the same name, usually within seconds and within two minutes for NetExec `main`. A 7045 has no matching removal event among the log sources above, so check whether the service is gone minutes later: its `HKLM\SYSTEM\CurrentControlSet\Services\<name>` key, or a later service inventory. Where Sysmon logs registry key deletes under that path (event 12, RegistryEvent object create and delete; Vendor docs: [Sysmon](https://learn.microsoft.com/en-us/sysinternals/downloads/sysmon)), the key's removal is the pair; that it captures the Service Control Manager removing the key is a Guess, not checked on a capture. Remote-exec tools install, run and remove; real software rarely does. A root 8-letter `RegistrationTrigger` task with no 4699 is not a clean miss: on Server 2025 a v1.5.1 task may never run and linger (Their code plus a Guess, see detection 3).
4. **Share write probes.** With 5145, look for one source creating and deleting a 10-letter directory or `.txt` file on several shares within seconds (NetExec up to v1.5.1).
5. **SMB1 sweep.** Where SMB1 access auditing is on, list sources with event 3000 on many servers in a short window; NetExec probes SMBv1 first on every host unless told not to (Their code). Vulnerability scanners do the same, so exclude them by address.
6. **Old-mode SAM/LSA reads.** With 5145, look for `ADMIN$` reads of `Temp\` plus 8 letters and `.tmp` (Their code: Impacket `secretsdump.py` at `caba5fac`); SigmaHQ `252902e3` looks under `SYSTEM32\` instead.
7. **Files left behind.** Search `C:\Windows\Temp\` for files named with exactly 6 or 8 letters and no extension, and `C:\windows\temp\` for GUID-named `.txt` files. NetExec deletes them after reading, so expect them only where a run failed part-way (Their code: v1.4.0 "Always delete output file", #568).

## Honest limitations

The three detections key on command, task and service templates read in NetExec's source, not on captured events. Every match result above comes from synthetic events built from that source, so the logic can still miss if Windows logs the strings differently, for example a different quoting of the task command line or task XML stored differently from how it was registered (detection 1 was made robust to expanded or literal environment variables in the ImagePath). Running NetExec in a lab and replaying the logs through the logic is the first thing to do before trusting them. NetExec is open source and changes often: an operator can edit any template in minutes, and the project itself randomised atexec in 2025 in a pull request titled "help bypass detection" (Vendor docs: PR #721); treat these detections as a cheap high-precision layer on top of the generic remote-execution, named-pipe and logon detections, never instead of them. The default SAM and LSA dump since v1.4.0 writes no files, and the old mode now writes under `C:\Windows\Temp`, so the classic secretsdump file rules, which look under `System32`, stay quiet for both; only the `svcctl`, RemoteRegistry and `\winreg` signals remain. With `--no-output`, wmiexec, mmcexec and atexec drop the output redirect that detection 2 keys on; for those runs only detections 1 and 3 still match NetExec templates, and wmiexec and mmcexec fall back to generic WmiPrvSE or mmc child detections. The first 4688 of an atexec task and the 4699 timing also differ on Server 2025 (see detection 3). The fan-out hunt groups by `IpAddress`, so NTLM logons logged without an address drop out of it (Guess, from Microsoft's note that NTLM logons may have no TCP/IP details), and 4776 on domain controllers carries no source for NetExec at all. NetExec can authenticate with Kerberos (Their code: `nxc/cli.py`), which removes the NTLM signals entirely. Spraying with one password per account per lockout window can stay under every threshold, and Defender for Identity's remote execution alerts only watch domain controllers, AD FS and AD CS servers. The empty-workstation hunt rests on how Impacket fills the NTLM message, which a future Impacket or NetExec release could change.
